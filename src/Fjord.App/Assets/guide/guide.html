Logging in with SSH keys

Swap passwords for a key pair: faster logins, nothing to type, and nothing for an attacker to guess.

The idea in one paragraph. A key pair is two files. The private key (id_ed25519) stays on your PC — never share it. The public key (id_ed25519.pub) is one line of text that you put on every server you want to log in to, in ~/.ssh/authorized_keys. When you connect, the server checks that you hold the private key that matches — no password is sent.

1Create a key

In Fjord: Key generator in the sidebar. Choose Ed25519, optionally set a passphrase, and save to the suggested location C:\Users\you\.ssh\id_ed25519. That folder is also where Windows' own ssh.exe, Git and VS Code look for keys.

Same thing from a terminal (Windows PowerShell, Linux or macOS):

ssh-keygen -t ed25519 -C "kim@laptop"

Passphrase or not? A passphrase encrypts the private key file, so a stolen copy is useless. Fjord asks for it once per session. Without a passphrase, anyone who copies the file can log in as you.

2Put the public key on the server

Easiest: let Fjord do it

  1. Connect to the server the usual way (with your password).
  2. Click Install key in the session toolbar and pick your .pub file.
  3. Fjord adds it to ~/.ssh/authorized_keys, fixes the folder permissions and skips it if it's already there. It then offers to switch the session to key login.

By hand (any SSH client)

Copy the whole line from the .pub file (Key generator → Copy public key), log in to the server and run:

mkdir -p ~/.ssh && chmod 700 ~/.ssh
echo 'ssh-ed25519 AAAA...paste...the...whole...line kim@laptop' >> ~/.ssh/authorized_keys
chmod 600 ~/.ssh/authorized_keys

From a Linux/macOS machine that already has the key: ssh-copy-id -i ~/.ssh/id_ed25519.pub user@server

3Switch the session to the key and test

Edit the saved session → Authentication: Private key → choose the private key (the file without .pub). Connect. If it logs in without asking for the server password, you're done.

If the key is refused, Fjord falls back to asking for your password, so you won't be locked out of the session.

4Optional: turn off password logins on the server

Do this only after step 3 works, and keep one session open while you test with a new one. If you lock yourself out, you'll need console access (VM console, iDRAC/iLO, physical keyboard).

Edit /etc/ssh/sshd_config (with sudo nano) and set:

PasswordAuthentication no
KbdInteractiveAuthentication no
PubkeyAuthentication yes

Check the drop-in folder too — files there win over the main file. Ubuntu cloud images often have 50-cloud-init.conf with PasswordAuthentication yes:

grep -ri passwordauthentication /etc/ssh/sshd_config.d/

Test the config and reload (the service is ssh on Debian/Ubuntu, sshd on RHEL/Fedora/Alma):

sudo sshd -t && sudo systemctl reload ssh

5Windows servers (OpenSSH Server on Windows)

Account typeWhere the public key goes
Normal userC:\Users\<user>\.ssh\authorized_keys
Member of AdministratorsC:\ProgramData\ssh\administrators_authorized_keys — the per-user file is ignored for admins

The admin file must only be accessible by Administrators and SYSTEM, or sshd ignores it. In an elevated PowerShell:

Add-Content -Path C:\ProgramData\ssh\administrators_authorized_keys -Value 'ssh-ed25519 AAAA... kim@laptop'
icacls.exe C:\ProgramData\ssh\administrators_authorized_keys /inheritance:r /grant "Administrators:F" /grant "SYSTEM:F"

Fjord's Install key button only handles Linux/Unix servers.

6Existing PuTTY keys (.ppk)

Fjord reads .ppk files directly — just point the session at them. To use the same key with OpenSSH tools (Windows ssh.exe, Git, Linux), convert it:

  • PuTTYgen: Load the .ppk → Conversions → Export OpenSSH key (force new file format).
  • Linux: puttygen key.ppk -O private-openssh-new -o ~/.ssh/id_ed25519

The public key line for authorized_keys is shown at the top of PuTTYgen ("Public key for pasting into OpenSSH authorized_keys file").

7Troubleshooting "Permission denied (publickey)"

  • Permissions on the server. sshd silently ignores keys if the files are too open: 
    chmod go-w ~
chmod 700 ~/.ssh
chmod 600 ~/.ssh/authorized_keys
  • Wrong user. The key is installed for one account only — root and kim have separate files.
  • Broken line. The key must be one line in authorized_keys. Pasting from some editors adds line breaks.
  • SELinux (RHEL/Alma/Fedora): restorecon -R ~/.ssh
  • See why the server refused: sudo journalctl -u ssh -n 50 (or -u sshd), or /var/log/auth.log.
  • Wrong file chosen. The session needs the private key (no .pub); the server needs the public one.

8Good habits

  • One key per PC. If a laptop is lost, remove just that line from authorized_keys on your servers.
  • Use a meaningful comment (kim@work-laptop) so you can tell keys apart later.
  • Back up your private key somewhere safe if re-installing the key everywhere would be painful — or just make a new one.
  • Never paste a private key into chat, email or a ticket. If it happens, generate a new key and remove the old public key from servers.
